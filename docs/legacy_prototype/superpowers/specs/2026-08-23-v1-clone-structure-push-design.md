# git_agent_app — v1 Design: Clone → Structure → Push

## Goal

Single task, end to end: connect GitHub, clone a repo to device, pick a file from it,
have an LLM restructure its content per bundled `structure.md` rules, refine via chat,
choose a save location in the repo, commit and push.

No skills/sub-agents/framework-switch/multi-tool agentic features in v1 — those are a
later spec once this pipeline works.

## Stack

- Flutter/Dart (matches `voice_notes_app`, already in this workspace)
- `git2dart` + `git2dart_binaries` — FFI bindings to the real libgit2 C library, with
  prebuilt native libraries bundled by the companion package (no manual NDK/CMake setup
  needed). (History: spec'd as `dart_git`, abandoned — v0.0.2, 5 years stale, no push
  support. Swapped to `git_on_dart` during planning — looked active but during
  implementation (Task 8) its own source was found to stub out HTTPS packfile transfer
  entirely, so clone never writes objects and push sends a request GitHub rejects.
  Swapped again to `git2dart`, which wraps real libgit2 rather than reimplementing the
  git wire protocol in Dart.)
- `dio` — GitHub REST API calls (repo listing) and cloud LLM HTTP calls
- `flutter_secure_storage` — encrypted storage for the GitHub PAT and any cloud API key
- Reuse `voice_notes_app`'s LLM engine abstraction as a starting point:
  `AnalysisEngine`, `CloudApiEngine`, `OnDeviceLlamaEngine`, `EngineFactory`,
  `EngineSettings` (lib/engine/*, lib/settings/engine_settings.dart) — ported and
  retargeted for repo-structuring prompts instead of voice-note analysis.

## GitHub auth

Personal Access Token (classic or fine-grained, `repo` scope), generated by the user at
github.com/settings/tokens and pasted once into Settings. Used as:
- Bearer token for GitHub REST API (list user's repos)
- HTTPS Basic auth credential for `dart_git` clone/push (no SSH keys)

Stored via `flutter_secure_storage`. Never logged.

## Screens

1. **Settings**
   - GitHub PAT field
   - LLM engine choice: Cloud API vs On-device (gguf), switchable
     - Cloud: endpoint, API key, model name, optional extra headers
     - On-device: file picker to select a local `.gguf` model path
   - `structure.md`: bundled default; import a replacement from local storage; export
     (share/save) the currently active one
2. **Repo list** — fetched from GitHub API using the PAT; tap a repo to clone
   (`dart_git`) into the app's internal storage under a per-repo folder (repo name).
   Re-selecting an already-cloned repo re-clones/overwrites.
3. **File browser** — tree view of the cloned repo; tap a file to use as the
   structuring source.
4. **Chat / refine screen**
   - Shows the source file content was loaded
   - Sends source content + `structure.md` rules to the active LLM engine, displays the
     structured Markdown result in the chat
   - User can send follow-up chat messages ("make it shorter", "add a frontmatter
     section") to request regeneration; LLM re-runs and posts updated result
   - Save location: either browse the repo's file tree and pick a target folder, or
     tell the LLM in chat where to save it (e.g. "save it in docs/posts/") — the app
     resolves that instruction to a repo-relative path
   - **Push** button: writes the file at the resolved path, `git add` + `commit` +
     `push` via `dart_git`

## Data flow & error handling

- PAT and cloud API key: encrypted storage, never logged or included in error text
  verbatim.
- Clone target: app internal storage, one directory per repo.
- Chat conversation: in-memory per session only — no persistence needed for v1; once
  pushed, the session's job is done.
- LLM not configured (no cloud key, no on-device model path set): block with a clear
  "configure LLM in Settings" message in the chat screen. Do NOT fall back to a fake/
  placeholder engine here — unlike voice_notes_app's fake-engine fallback, silently
  faking structured content and pushing it to a real repo is an unacceptable failure
  mode.
- Push failures (auth rejected, network error, non-fast-forward conflict): surfaced as
  plain error text in the chat screen. No silent retry, no offline queue in v1.
- `git2dart` clone/commit/push against a real GitHub repo is unverified in practice as
  of plan-writing time. Task 8's smoke test against a real throwaway repo is the point
  where this gets confirmed — this is the second library swap for this exact reason
  (the first, `git_on_dart`, turned out to stub out HTTPS packfile transfer entirely).

## Testing

No automated UI test suite for v1 (manual run against a real throwaway repo). Any
non-trivial logic — specifically the chat-instruction-to-repo-path resolver — gets one
small `test_*` covering at least: explicit path from user, path with/without trailing
filename, ambiguous/missing input.

## Explicitly out of scope for v1

- Real-time OAuth device/web flow (PAT only)
- Skills / sub-agents / instructions library UI
- LangChain/LangGraph or other agent framework integration
- Generic git actions UI (branch/diff/merge/etc.) beyond commit+push of the one file
- Any repo other than the currently selected/cloned one
- Persisting chat history across sessions
